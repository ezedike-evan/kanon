# Kanon — Security

This is the section the submission is judged on. It states what the contracts
enforce, what they trust, and what is still open. Where something is not built
or not verified, it says so.

Status as of 2026-09-20: nothing here has been audited, deployed to Monad
mainnet, or run against a live Convex, Privy, Perpl or Kuru account. What is
claimed as verified is verified by the test suites named at the end.

Gaps 12 to 15, the additions to gaps 1, 2, 6 and 9, and the notes above them
that point to those gaps are as of 2026-10-13. They were checked against the
source, not against a running deployment.

## The claim

A trader pins a rule. A contract refuses any trade that does not satisfy it.

"The rule" is three things pinned together in `StrategyRegistry`:

- `specHash`: SHA-256 of the canonical spec JSON. Identifies the rule for humans
  and for the evidence chain. The chain cannot recompute it. Risk per trade and
  stop distance are bound only by this hash, and no contract reads them (gap 1).
- `predicatesCommitment`: `keccak256(abi.encode(PredicateDefinition[]))`. This is
  what the chain actually checks. `packages/spec` `encodePredicates(spec)` produces
  the exact bytes, and a test vector generated by Solidity proves the two agree.
- `series`: the canonical price series (asset, feed, cadence, bucket) the
  predicates are evaluated over.

`RefusalGate.evaluateOnChain(strategyId, isLong, predicates)` takes the series
from the registry, requires the supplied predicates to hash to the pinned
commitment, derives the scan window on-chain from the series' latest bucket and
each predicate's committed lookback, requires a fresh sample, evaluates the three
predicates (break of structure, fair value gap, liquidity sweep) as integer
arithmetic in `PredicateEngine`, and checks that the trade side agrees with the
predicates' direction. It returns a refusal naming the failing predicate and the
number that failed. Approval stores nothing and cannot be replayed.

Where funds move, approval is required in the same transaction:
`GuardedVault.proposeTrade`, `MarginAccount.openGuardedPosition` (after a one-way
`bindStrategy`) and `CopyVault.mirrorOpen`. Approval covers the predicates and
the side. It does not cover the size of the trade, and the vaults' projected
result and prices are supplied by the caller, not derived by the contract
(gap 13).

On the testnet deployment the price series is fed by a mock anyone can set
(gap 12). Everything in this section holds there as arithmetic over a tape
anyone can write.

## The contract never calls a model

No Solidity function in this repository calls, waits on, or accepts the output of
a model. Every function resolves to signature verification and arithmetic over
on-chain state. The contract cannot be talked into anything.

The model sits in one place, the compiler, which translates plain language into a
spec. It is untrusted by construction:

- Output is validated against the Zod schema and retried on failure. Partially
  valid output is never accepted.
- The user always reviews the spec in plain English and in parametric form. Every
  default the compiler inferred is listed and editable. Pinning is blocked until
  the user confirms they have read it.
- The model version is pinned and the compiler is snapshot-tested against a
  fixture set.

If the compiler is wrong, the user sees it before pinning. If the compiler is
malicious, it still cannot pin, because only the user's wallet can.

## Why a second AI is not the verifier

Two models agreeing is correlation, not verification. They correlate hardest
where both are wrong. So no model, and no pair of models, sits inside the trust
boundary.

The design in `docs/ARCHITECTURE.md` gives a second agent one role: a challenger
that searches for evidence making a claim arithmetically false. Its opinion has
no weight; only signed price data does. **That challenger is not built in this
submission.** It was out of scope (`docs/SCOPE.md`). The current system needs no
challenger, because the contract evaluates the predicates itself from the
canonical series rather than accepting a claim.

## What is trusted

| Trusted | Why it matters | Assumption |
|---|---|---|
| Pyth's on-chain price on Monad | Every predicate and every settlement reads it | Not manipulated. Documented, not solved. On testnet it is a mock anyone can set (gap 12). |
| Monad consensus | Ordering and finality | Standard chain assumptions |
| The user's own review of the spec | The only place intent is checked | The user reads it |
| The pinned model version | Compiler quality only, never safety | Not needed for safety |

**Feed manipulation.** A pushed price could fake a break of structure. The series
is event-driven (0.02% deviation, 1h heartbeat for the sponsored feeds), so a
single manipulated print can become a candle. We do not claim this is solved. The
canonical series makes it visible and reproducible, since anyone can recompute
the same candles from the same samples, but it does not prevent it.

## Threats and what was done

| Threat | Mitigation | Residual |
|---|---|---|
| Proposer supplies easier predicates, a friendlier window, or another series | Commitment and series pinned in the registry; window derived on-chain | None found. Adversarial tests cover each. |
| Stale series approves a trade | Freshness required at evaluation | A quiet feed delays approval rather than allowing it |
| Trade opposite to the rule's direction | Side bound to predicate direction; mixed-direction rules rejected | None found |
| Attested (caller-supplied) result approves a trade | The attested `evaluate` path was deleted | None for the predicate result. Other caller-supplied figures remain (gap 13) |
| Loosening a rule mid-drawdown | Loosening waits out a cooling-off in the registry; tightening is immediate; no admin path | The check covers predicates only, not sizing or stops. See "tighten vs loosen" below |
| Loosening via a new looser vault | `VaultFactory` hold for factory-created vaults | Other owner addresses, new strategies and `CopyVault` limits are not covered |
| Staking on Predict after the outcome is known | `ThresholdMarket` reverts once the series shows a crossing, and requires a fresh sample | None found |
| Acting as another user in the backend | Privy JWT with Convex custom-JWT auth; identity derived from the token; a test fails any public function that takes a user id | The Privy handshake has not run against a live deployment |
| Client writing account collateral or positions | Those writes are internal to the backend | Not verified live |
| Unhealthy accounts left open | Permissionless liquidation and de-leveraging, plus a keeper we run | The liquidator earns nothing on-chain. Both revert while the series has no sample in the current bucket (gap 14) |
| Loss beyond collateral | Recorded as debt; insurance fund draws only when no positions remain; the fund has no owner and no withdrawal | No liquidity pool backs winners' profit |

## Known gaps (do not assume these are done)

1. **Tighten vs loosen is enforced on-chain, conservatively.** `tighten` takes the
   old and new predicate arrays, checks both against their commitments, and accepts
   only a same-series change where every existing predicate is identical except
   `minGapBps` may rise, plus appended predicates. Anything else (including a longer
   lookback, whose direction is ambiguous) reverts `NotATightening` and must go
   through `proposeLoosening`. `packages/spec` mirrors the rule exactly.
   What this proves is that the predicate list is no looser, and nothing else.
   `tighten` writes the new `specHash` in the same call with no cooling-off, and
   unchanged predicates pass the check, so an owner can replace the hash at any
   time. Risk per trade and stop distance never reach a predicate: they are
   bound only by that hash, which the chain cannot read, and no contract checks
   a trade's size or stop against them. On-chain they can change at once, in
   either direction. `packages/spec` classifies more risk or a wider stop as a
   loosening (`diff.ts`); that classification runs off-chain and the registry
   does not enforce it.
2. **No liquidity pool backs profits.** `MarginAccount` is a ledger. Real
   execution goes through Perpl only, on testnet (gap 9), and nothing is
   executed on Kuru (gap 6); nothing on-chain pays out a winning
   `MarginAccount` position.
3. **The liquidator is unpaid.** The keeper's gas is our cost.
4. **Vault, follow and position records in Convex are claims,** not on-chain
   proofs. Someone could pre-record another user's vault address. Verifying
   against `VaultFactory.isVault` on-chain is not built.
5. **No per-user rate limit** on the compiler or Nansen. The compiler now caps
   input size and has a timeout; a limiter is still to do.
6. **Not exercised live:** Perpl order encodings, the Perpl three-step
   safeguard (API key, `createAccount`, `allowOrderForwarding`), all Kuru
   on-chain behaviour, the Envio indexer against a chain, Nansen's real API,
   Privy's token handshake. Kuru is not integrated:
   `packages/execution/src/kuru.ts` is a client library for markets that
   already exist on Kuru. Nothing outside `packages/execution` imports it;
   inside, only the venue router calls it, and no running process builds that
   router. It has never run against Kuru.
7. **No third-party audit.**
8. **Mainnet scope is the core only.** `Deploy.s.sol` on chain 143 refuses mocks and
   skips `MarginAccount`, `InsuranceFund` and `VaultFactory` (gap 2). `CanonicalSeries`
   now rejects non-positive prices, positive exponents and confidence wider than 2%.
9. **Executed trades are paper fills** and are labelled so (`executionMode`).
   A rule on autopilot is the exception: its pass sends a real testnet order
   while its row stays labelled paper (gap 15).
   Separately, the chart's order ticket can place a real market order on Perpl
   testnet through the gateway's `/trade` routes. That path uses one API key
   held by the gateway process, so every user trades the same exchange account;
   it does not consult the pinned rule, and it is bounded by the limits in
   `packages/execution/src/venue-policy.ts`. It is a demonstration of
   execution, not per-user trading and not custody. Two things follow from
   where it runs. The gateway is also the public market data server, so a
   fault in it is a fault in a process that holds a trading key (an API key
   can trade; it cannot withdraw). And Perpl refuses its trading API to some
   regions (HTTP 451): the gateway has to run where Perpl serves, and a user
   in a region Perpl does not serve could still reach the shared account
   through it. That is acceptable for a testnet demonstration and is not for
   real funds. Predict's timed trades go through the same path and the same
   account. Their closing order is sent by the gateway on its own authority
   when the time is up, and nothing closes a timed trade while no gateway is
   running: the position stays open until one starts and reads the running
   trades back.
10. **Audit findings fixed in contracts:** `ThresholdMarket` now settles on the exact
    window (per-sample publish times from `CanonicalSeries`, inclusive at both ends;
    `settle` waits `maxPriceAgeSeconds` past `windowEnd`; `takeSide` also refuses a
    live Pyth price that already crosses). All ERC20 movement uses a local SafeERC20
    with an exact-receipt check (fee-on-transfer tokens are rejected, not credited
    short) and a local `nonReentrant` guard. `StrategyRegistry` has a two-step
    bond exit (`requestRetire`, then `finalizeRetire` after the loosening cooldown;
    no admin, no slashing); retired strategies fail closed in `RefusalGate`. Dust
    positions are now deleverageable (slice rounds up).
11. **Partly closed on 13 October.** A pin, a change to a pinned rule and an
    applied loosening are each written only after the backend reads the
    transaction's receipt and finds the registry's own event for that strategy
    id in it: for a pin, `StrategyPinned` from the caller's linked wallet with
    the draft's hash, commitment and series, and the bond recorded is the one in
    the event (`strategies.ts`, `chainLogic.ts`). A transaction hash on its own
    records nothing, and with the registry not configured nothing is pinned.
    Autopilot, which sends orders to the venue, runs only a rule pinned that
    way. Before this a signed-in user could mark a draft pinned with a made-up
    hash and no bond. **Still open:** the hash given when a pending loosening
    is withdrawn is not checked (that row only ever moves back to the stricter
    spec), and equity is not verified server-side.
12. **The testnet oracle is a mock anyone can set.** `deployments/10143.json`
    records `"mocks": true`: the two series on chain 10143 read a `MockPyth`
    (`test/mocks/MockPyth.sol`) whose `setPrice` has no access control, and the
    collateral token is a `MockERC20` with an open `mint`. `recordSample` is
    permissionless, so anyone can set a price, record it, and decide whether
    the gate approves or refuses a testnet trade and what a testnet margin
    position or threshold market settles on. Anyone can also stall the series:
    while the mock holds an exponent other than the one first recorded,
    `recordSample` reverts. `CanonicalSeries` still rejects a non-positive
    price, a positive exponent and a confidence wider than 2%; none of that
    makes the number true. On mainnet `Deploy.s.sol` refuses mocks and the
    series reads Pyth's own contract. That deployment has not been made.
13. **The vaults act on figures their executor reports.** The gate decides
    whether the pinned predicates hold. It does not see what the vault then
    does with the answer. `GuardedVault.proposeTrade` takes `projectedPnL` from
    its caller (the vault's owner or its `strategyExecutor`) and adds it to the
    day's realised P&L, so the daily drawdown cap is checked against a reported
    number, not one the contract derives. A caller that reports zero is never
    refused by the cap. `size` is written to the event and checked against
    nothing. `CopyVault.mirrorOpen` and `mirrorClose` take the leader's size and
    the entry and exit prices from `leaderExecutor`. The follower's result is
    computed from those reported prices and applied to the follower's ledger: a
    false exit price can credit a profit no token backs, or write the
    follower's withdrawable balance down to zero. The mirrored size is
    `leaderSize` scaled by `allocationBps` and is not bounded by the follower's
    collateral. Neither vault reads a `CanonicalSeries` for these figures or
    observes a fill. The mainnet deployment script skips the factory that
    creates them (gap 8).
14. **A stale series stops `MarginAccount`.** Every price it uses is the close
    of the series' current bucket (`_currentPrice`). With no sample in that
    bucket it reverts `NoRecentPrice` instead of using an older price.
    `openPosition`, `openGuardedPosition`, `closePosition`, `liquidate` and
    `deleverage` all need that price, and so does `withdraw` for an account
    with an open position. While the series is stale an unhealthy account
    cannot be liquidated or de-leveraged and its owner cannot close it. An
    account with no open position can still withdraw. Anyone can end the stall
    by calling `recordSample()`, but a sample lands in the bucket of the feed's
    own publish time, so it helps only once the feed holds a price published in
    the current bucket. The price series keeper is not running continuously
    (README, Status), so on testnet this is the usual state between runs.
15. **Autopilot sends real testnet orders on a verdict reached off-chain, and
    does not trade the rule's own entry, size or stop.** With autopilot on, the
    backend judges a pinned rule once per closed candle of its own timeframe
    (`autopilot.ts`, a sweep every minute), with the arithmetic a button press
    runs over the backend's own candles. The on-chain gate is not called. A
    pass is written as a proposal. The gateway polls for proposals and opens
    each as a timed trade on Perpl testnet in the rule's market and on its
    side: a $10 stake at the timed-trade leverage (5x, or the market's own
    maximum where that is lower; `timed-policy.ts`), held for the shortest of
    1, 5, 15 or 60 minutes that is not shorter than the rule's candle, or 60
    minutes for a longer candle. The entry is whatever a market order fills at,
    up to two minutes after the verdict. The size is the stake times the
    leverage, not the rule's risk per trade. There is no stop at the rule's
    distance: a timed trade ends when its time is up, when its loss reaches the
    stake at the mark price, or when its owner ends it. The proposal's row
    keeps the rule's own entry, size and stop and stays labelled `paper`. Every
    user's autopilot trade goes to the shared account of gap 9, where a market
    holds one position, so a pass opens nothing while that account already
    holds a position in the market. Not yet run end to end on the live
    deployment.

## Perpl safeguard

Enrolling an API key does not authorise trading. A wallet must separately call
`createAccount` and `allowOrderForwarding(true)`. The execution client refuses
locally when forwarding is off, and it defaults to paper mode unless
`KANON_EXECUTION_MODE=live` and credentials are present. The execution layer
cannot grant itself trading rights.
